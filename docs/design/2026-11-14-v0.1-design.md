# Audit Analytics Workbench — v0.1 design

Status: draft for approval · Date: 2026-11-14

## 1. Intent

A local-first, open-source toolkit that runs audit data-analytics tests on a
client extract, checks the integrity of the extract first, ranks exceptions
against materiality, and writes a reviewable Excel workpaper.

It is a portfolio piece for Technology Risk Assurance (ITGC + data analytics)
and, later, a base the IT-audit community can extend by adding folders.

The tool **flags and ranks**. A person decides whether an exception is an
error, a false positive, or needs a client query. The tool never concludes
and never signs off.

## 2. Goals, non-goals, anti-goals

**Goals (v0.1)**
- Any tabular source (CSV / Excel) can feed any test, through a mapping file.
- Integrity gate (completeness and accuracy of the extract, i.e. IPE) runs before any test.
- Six test packs, two synthetic datasets (retail and general ledger), one engine.
- Same input + parameters ⇒ byte-identical exceptions list.
- New test = new folder (`test.sql` + `meta.yaml`), no engine change.

**Non-goals (v0.1)**
- Streamlit review screen beyond §5.9a (no editing of exception data, no reruns from the screen).
- Benford analysis, statistical sampling, connectors to client databases.
- Concluding on exceptions, scoring audit risk, or writing opinions.

**Anti-goals (failure even if it "works")**
- Any network call, telemetry, or AI service at runtime.
- Any silent change to data (placeholder → null, type coercion, dropped row) that is not counted and shown.
- The tool filling a disposition, conclusion, preparer or reviewer field.
- Real client data, or anything derived from it, in the repository or its history.
- A pack able to read or write files other than the mapped sources.

## 3. Constraints

- Python ≥ 3.11. Dependencies pinned: `duckdb==1.5.6`, `pandas==3.0.5`,
  `openpyxl==3.1.5`, `PyYAML==6.0.3`, `pytest==9.2.0`. CLI uses `argparse`.
- No dependency may make network calls at runtime. DuckDB extension
  auto-install/auto-load is disabled.
- Money is never floating point: amounts are `DECIMAL(18,2)` from load to output.
- Only generated files in `sample_data/` may be tracked. `private/`, `data/`,
  `input/`, `output/`, `outputs/` and all other `*.csv` / `*.xlsx` are gitignored.
- Repository: private GitHub repo `audit-workbench`, MIT licence. Visibility
  changes only on the owner's explicit decision, after the pre-publish checklist.

## 4. Approaches considered

| Approach | Trade-off | Decision |
|---|---|---|
| **A. One fixed canonical schema** (`sales`, `employees`, …); mapping fills it; tests query it | Simple engine, but every test is tied to retail concepts; a GL or HR extract needs schema changes | Rejected |
| **B. Per-pack input contracts** — each pack declares the roles and fields it needs; the mapping binds any dataset to them | Slightly more mapping to write; generic tests reusable across datasets; new datasets need no engine change | **Chosen** (owner's decision) |
| C. Python-coded tests | Most flexible, but tests stop being portable, reviewable SQL | Rejected |

## 5. Design

### 5.1 Commands

```
workbench validate-mapping MAPPING.yaml [--packs DIR]
workbench run MAPPING.yaml --config config.yaml --out OUTPUT_DIR
              [--engagement "Name"] [--force] [--packs DIR]
```

`validate-mapping` loads nothing but headers. It checks the YAML structure,
that every source file/sheet exists, that every mapped column is in the
header, that every `runs[*].bind` satisfies the pack's contract (role exists,
every required field bound, types compatible), that parameters match the
pack's declared parameters, and that keys/references point at real fields.
Every problem is reported in one pass, each as
`mapping.yaml:<yaml path>: <what is wrong> — <how to fix>`. Exit code 0/1.

`run` = validate → load → integrity gate → run packs → materiality → write
`workpaper.xlsx`, `exceptions.jsonl` (deterministic, sorted, no timestamps)
and `runlog.json`. A gate `fail` stops before packs unless `--force`; the
force is recorded in the run log and on the Cover and Integrity sheets.

### 5.2 Mapping file — two layers

Example mappings are fully commented, line by line, so a user can copy one
and adapt it for their own extract.

```yaml
mapping_version: 1
null_placeholders: ["N/A", ""]          # converted to NULL, counted per column

datasets:                               # layer 1: load once, integrity gate works here
  sales:
    source: {file: sample_data/retail.xlsx, sheet: Sales}
    columns:                            # dataset field: {from: source column, type: ...}
      sale_id:      {from: SaleRef,   type: string}
      sale_date:    {from: SaleDate,  type: date}
      customer_id:  {from: CustRef,   type: string}
      total_amount: {from: Total,     type: decimal}
      employee_id:  {from: StaffRef,  type: string}
    primary_key: [sale_id]
    references:                         # foreign keys, checked both directions
      - {fields: [employee_id], to: employees, to_fields: [employee_id]}
    sequence: {field: sale_id, pattern: '^S(\d+)$'}   # optional, for gap check
    control_totals: [total_amount]                     # optional, default: all decimals
  # ...

runs:                                   # layer 2: pack instances
  - id: REV-01
    pack: general/duplicates
    bind:
      records:                          # contract role -> dataset
        dataset: sales
        fields: {record_id: sale_id, date: sale_date, amount: total_amount}
    params:
      key_fields: [customer_id, total_amount, employee_id]
      date_tolerance_days: 0
```

Rules:
- Source columns are matched by exact header. A **missing** mapped column
  rejects the file. An **extra, unmapped** column is never loaded; only its
  name is logged as "ignored" (this keeps personal data such as names, phone
  or ID numbers out of the engine).
- The same pack may appear in several `runs` with different bindings.
- A run whose bound dataset is absent is **skipped and logged**, not failed.
- The real-data mapping a user writes for their own extract lives outside the
  repo (e.g. `private/`); only the two synthetic example mappings are tracked.

### 5.3 Loader

- Reads every cell as text (`dtype=str`, `keep_default_na=False`), so pandas
  never converts anything implicitly.
- Applies `null_placeholders` explicitly; counts each conversion per column.
- Types: `string`, `integer`, `decimal` (→ `DECIMAL(18,2)`), `date`,
  `boolean`. Conversion happens in DuckDB from the text value (`TRY_CAST`),
  so no float is involved. Any non-placeholder value that fails to convert is
  counted and listed (row number + column, no value echo in logs beyond the
  workpaper) and is a gate `fail`.
- Every coercion, placeholder conversion and rejected row is logged and
  appears in the Integrity sheet and run log.

### 5.4 DuckDB sandbox

One in-memory connection per run. Datasets are registered from memory, then:
`SET enable_external_access = false`, `SET autoinstall_known_extensions = false`,
`SET autoload_known_extensions = false`, `SET lock_configuration = true`.
Pack SQL therefore cannot `read_csv`, `COPY`, `ATTACH`, `INSTALL` or change
settings. A test proves a malicious pack that tries to read a file fails.

For each run, the engine creates views named after the contract roles
(`records`, `events`, `people`, …) with contract field names, so pack SQL
never sees source names. Pack SQL may only `SELECT`.

### 5.5 Pack format

```
packs/<group>/<name>/
  meta.yaml
  test.sql
```

`meta.yaml`: `id`, `name`, `objective`, `assertion`
(existence | completeness | accuracy | occurrence | cutoff | classification),
`risk`, `category` (itgc | financial | analytical), `contract`, `parameters`
(type + default), `amount_column`, `initial_label`
(likely_error | inquiry | control_deficiency), `needs_client_confirmation`,
`limitations`.

```yaml
contract:
  records:
    required: {record_id: string, initiator: string, approver: string}
    optional: {amount: decimal, date: date}
parameters:
  key_fields: {type: field_list, role: records, default: []}
  date_tolerance_days: {type: integer, default: 0}
```

Parameters:
- Value parameters are passed as DuckDB bound parameters (`$date_tolerance_days`).
- `field_list` parameters are substituted with `{{key_fields}}`, only after
  each name is checked against the role's bound fields and quoted as an
  identifier. No other text substitution exists.

`test.sql` returns one row per exception with a stable `exception_id`, the
key fields, `amount_at_risk` (nullable, DECIMAL) and optionally `rule` and
`group_id`. The engine sorts exceptions by `exception_id` for determinism.

### 5.6 Integrity gate

Runs on the `datasets` layer, before any pack. Output → Integrity sheet.

| Check | Status if found |
|---|---|
| SHA-256, size, modified time per source file | info |
| Source vs loaded row counts differ (truncation / rejected rows) | **fail** |
| Mapped column missing | **fail** (file rejected) |
| Duplicate primary key | **fail** |
| Unparseable non-placeholder value | **fail** |
| Declared `balance_check` group not summing to 0 within tolerance | **fail**, message: "possible incomplete extract" |
| Control totals (sum of decimals, date min/max, distinct keys) | info |
| Null / placeholder count and % per column | warn if > 0 placeholders (shown), info otherwise |
| Referential integrity, both directions | warn |
| Sequence gaps (declared `sequence`) | warn |

`balance_check` is declared per dataset:
`balance_check: {group_by: [je_id], amount: amount, tolerance: 0.01}`.

### 5.7 Packs (v0.1)

| ID | Pack | Roles → logic | Label |
|---|---|---|---|
| ITGC-01 | `itgc/leaver_activity` | `events(actor, event_date)`, `people(person_id, leave_date, status)`. Rule `after_leave`: event after the actor's leave date. Rule `leaver_still_active`: leave date set but status in `active_values` (default `["Active"]`). | control_deficiency |
| ITGC-02 | `itgc/segregation_of_duties` | `records(record_id, initiator, approver)`: initiator = approver. | control_deficiency |
| REV-01 | `general/duplicates` | `records(record_id, date, amount)` + `key_fields`, `date_tolerance_days` (0). Rows with a NULL key field are excluded (so placeholder customers are not "duplicates"). One exception per row in a group, shared `group_id`; `amount_at_risk` only on rows after the first, so the original is not counted twice. | likely_error |
| REV-02 | `general/sequence_gaps_orphans` | `sequence(id)` with `id_pattern`; optional `children(parent_id)`. Rules `gap` and `orphan`; flag `gap_matches_orphan` when an orphan's parent ID is exactly a missing sequence number. | inquiry |
| PAY-01 | `examples/commission_recalc_attribution` | Example of a domain-specific pack. `sales`, `commissions`, `people`. (a) `attribution`: commission employee ≠ sale employee. (b) `recalc`: \|commission − rate × total\| > `tolerance` (1.00), `needs_client_confirmation: true`. Summary adds "systemic: X% of rows" when (b) hits more than half the rows. | (a) likely_error, (b) inquiry |
| JE-01 | `gl/unusual_postings` | `lines(je_id, line_no, posting_date, amount)`. Rules `weekend` (`weekend_days`, default Sat/Sun), `holiday` (dates from `holiday_file`), `round` (\|amount\| is a multiple of `round_to`=1000 and ≥ `min_amount`=10000; computed in DECIMAL). One exception per line, `rule` lists all hits (`weekend;round`). | inquiry |

`holiday_file` is a YAML list of dates. The shipped
`sample_data/holidays_my_2025.yaml` is a Malaysian national public-holiday
list for the synthetic year, labelled at the top **"Illustrative sample — not
an authoritative calendar; supply your own."** It is read by the engine (not
by SQL) and registered as a table, so the sandbox stays closed.

### 5.8 Materiality and ranking

`config.yaml`: `overall` (illustrative default 50000, user must set),
`performance_pct` 0.75, `clearly_trivial_pct` 0.05. Bands per exception:
`above_materiality`, `above_performance`, `above_trivial`, `trivial`,
`no_amount`. Also aggregated per run (sum of `amount_at_risk`, highest band,
and the band the aggregate falls in). Sort: band, then amount desc, then
`exception_id`.

### 5.9 Workpaper (Excel)

Sheets: **Cover** (engagement, objective, run ID, tool version, date, inputs
with SHA-256, materiality, preparer/reviewer blank), **Integrity**,
**Summary** (one row per run: assertion, count, total at risk, highest band,
aggregate band, status ok/skipped/failed, systemic note), **one sheet per run**
(exceptions + `Disposition` dropdown: Error / Irregularity — inquire / Needs
client query / False positive / Accepted, `Reviewer note`, `Reviewed by`,
`Date`, all blank), **Limitations**, **Run log**. The tool never writes into
the four review columns.

### 5.9a Review screen (optional, block 5)

Purpose: a portfolio-grade way **into** the workpaper. Excel stays the official
record. Installed only with `pip install .[review]` (pinned `streamlit==1.67.0`);
the core tool never imports it.

```
workbench review OUTPUT_DIR [--port 8501]
```

- Reads `OUTPUT_DIR/workpaper_reviewed.xlsx` if it exists, else `workpaper.xlsx`.
- Overview: Summary and Integrity tables, and a chart of exception counts by
  materiality band per run (one-hue ordinal ramp, `no_amount` in gray).
- Exceptions: pick a run; filter by band, label and review status; table with
  a detail panel for the selected row.
- Disposition form: one of the five allowed values only, reviewer note,
  reviewer name (required) and date. Applies to the rows the reviewer selected,
  nothing else. The screen never proposes or pre-selects a disposition.
- Saves to `workpaper_reviewed.xlsx` (never the original), touching only the
  four review columns, and appends one `review` line per changed row to the
  copy's Run log sheet (run, exception, previous and new value, reviewer, time).
- Offline: `.streamlit/config.toml` and the launcher both force
  `browser.gatherUsageStats=false`, `server.address=localhost`,
  `server.headless=true`. A test launches the real server with a socket audit
  hook and fails on any non-loopback connection.
- Not in scope: editing exception data, rerunning tests from the screen.

### 5.10 Synthetic data

`tools/generate_synthetic.py --seed 42 --out sample_data/` writes:

- `retail.xlsx` — customers, employees, products, sales, sale lines,
  commissions, purchase orders, PO lines. Invented names; phone and ID
  numbers in clearly fictional formats (e.g. `000-FAKE-1234`), in columns the
  mapping does not load. Source headers deliberately differ from contract
  field names, to exercise the mapping.
- `gl.csv` — a small general ledger (je_id, line_no, posting_date, account,
  amount, description, posted_by, source), balanced per JE.
- `planted_issues.json` — every planted anomaly by run ID and key, plus seed.

Planted (retail): 6 sale IDs removed from sales but kept in commissions;
4 sales after an employee's leave date; 1 leaver still "Active"; 1 PO raised
and approved by the same person; 4 duplicate pairs (8 rows); 70+ commissions
attributed to another employee; commission ≠ rate × total for most rows;
~80% placeholder customers.
Planted (GL): 5 weekend, 3 holiday, 6 round-amount, 2 weekend+round lines.
Corrupted fixtures (tests only, generated at test time): missing column,
duplicate key, truncated rows, one unbalanced JE.

### 5.11 Acceptance criteria (v0.1 done when all pass)

1. `pytest` passes.
2. Both example runs find **every** planted issue (recall 100%); extra exceptions are counted and reported.
3. Re-run with identical input/params ⇒ byte-identical `exceptions.jsonl`.
4. A full run opens no network connections (`socket` monkeypatched to raise).
5. The gate fails on each corrupted fixture (missing column, duplicate key, truncated rows, unbalanced JE).
6. Workpaper opens in Excel; dropdowns work; review fields blank (checked via openpyxl).
7. A temporary pack folder added in a test runs with no engine change.
8. A pack that tries to read a file is blocked by the sandbox.
9. `validate-mapping` reports each kind of mapping error with a clear message and exit code 1.
10. Each example end-to-end run takes under 1 minute on a laptop.

### 5.12 Build order

1. `.gitignore` commit → design doc → skeleton, mapping schema + `validate-mapping`, loader, integrity gate.
2. Synthetic generator + planted issues, runner + sandbox, six packs.
3. Materiality, workpaper, run log.
4. Acceptance tests, README (with disclaimer), CONTRIBUTING, WRITING_A_TEST, MAPPING, LICENSE, CI file.
5. Review screen (§5.9a), optional extra.

If time is short, drop block 5 first. Never drop the integrity gate or the acceptance tests.

## 7. Left to the builder

Internal module boundaries, exact log formats, Excel styling, the shape of
`exception_id` (must be stable and derived from keys, never from row order),
and how `date_tolerance_days > 0` groups records (pairwise within tolerance is
acceptable; document the choice in the pack's limitations).
