# Audit Analytics Workbench

A local-first, open-source toolkit for audit data analytics. It checks the
integrity of a client extract first, runs SQL test packs over it, ranks the
exceptions against materiality, and writes an Excel workpaper for review.

> **Disclaimer.** This tool supports audit procedures; it does not replace
> professional judgment. It flags and ranks exceptions only — whether an
> exception is an error, a false positive or needs a client query is decided by
> a person. Provided under the MIT licence, **with no warranty**.

## What it does

1. **Validates a mapping** (`workbench validate-mapping`) that says which file,
   sheet and column fills which field, and how each test's inputs are bound.
2. **Loads the extract as text** (CSV or Excel). Placeholders such as `N/A` are
   converted to NULL explicitly and counted; every type conversion, rounding of
   float noise and rejected row is logged. Unmapped columns are never loaded.
3. **Runs the integrity gate** (completeness and accuracy of the extract):
   file SHA-256, row counts, declared record counts, duplicate keys,
   unparseable values, journals that do not balance, control totals, null and
   placeholder shares, referential integrity in both directions, sequence gaps.
   A failure stops the run unless `--force` is given, and the force is recorded.
4. **Runs test packs** — plain SQL in folders — inside a DuckDB connection that
   cannot read or write files, attach databases or reach the network.
5. **Bands exceptions** against overall, performance and clearly-trivial
   materiality, per item and in aggregate.
6. **Writes a workpaper** (`workpaper.xlsx`): Cover, Integrity, Summary, one
   sheet per test with a Disposition dropdown and blank review columns,
   Limitations, Run log. Also `exceptions.jsonl` (byte-identical on re-run) and
   `runlog.json`.

Offline by design: no network calls, no telemetry, no AI service at runtime.

## Quick start

```bash
python -m venv .venv && . .venv/bin/activate
pip install -r requirements.txt && pip install -e .

workbench validate-mapping mappings/example_retail.yaml
workbench run mappings/example_retail.yaml --config config.yaml --out output/retail --engagement "Demo (synthetic data)"
workbench run mappings/example_gl.yaml --config config.yaml --out output/gl
pytest
```

Set `config.yaml` materiality for your engagement before relying on the bands.

## Review screen (optional)

A local web page for working through a run's exceptions: filter by test, band, label and
review status, read each exception, and record **your** disposition, note, name and date.

```bash
pip install -e .[review]
workbench review output/retail
```

- It runs only on this computer (`localhost`) with Streamlit usage statistics switched off;
  tests check that neither the server nor the page contacts anything else.
- It never suggests or pre-selects a disposition.
- Decisions are saved to `workpaper_reviewed.xlsx` next to the original, filling only the four
  review columns, with one change-history line per decision in its Run log sheet. The original
  `workpaper.xlsx` is never modified. Excel remains the official workpaper.

## Test packs (v0.1)

| ID | Pack | Looks for | Initial label |
|---|---|---|---|
| ITGC-01 | `itgc/leaver_activity` | Activity after a person's leave date; leavers still shown as active | control deficiency |
| ITGC-02 | `itgc/segregation_of_duties` | Records raised and approved by the same person | control deficiency |
| REV-01 | `general/duplicates` | Records sharing key fields (a parameter) on the same date, with a day tolerance | likely error |
| REV-02 | `general/sequence_gaps_orphans` | Gaps in a document sequence; child records with no parent; where both coincide | inquiry |
| PAY-01 | `examples/commission_recalc_attribution` | Commission paid to another person; commission ≠ rate × total (example of a domain pack) | likely error / inquiry |
| JE-01 | `gl/unusual_postings` | Journal lines on weekends or public holidays; large round amounts | inquiry |

The generic packs work on any dataset: each declares an input **contract**
(roles and fields) and the mapping binds your data to it. See
[docs/MAPPING.md](docs/MAPPING.md) and [docs/WRITING_A_TEST.md](docs/WRITING_A_TEST.md).
Adding a test is adding a folder — no engine change.

## Sample data

Everything in `sample_data/` is synthetic, generated by

```bash
python tools/generate_synthetic.py --seed 42
```

Names are invented and phone and ID numbers use an obviously fake format.
`sample_data/planted_issues.json` lists every planted anomaly; the acceptance
tests check that every one is found. The holiday list
`sample_data/holidays_my_2025.yaml` is an **illustrative sample** of Malaysian
national holidays, not an authoritative calendar — supply your own.

## Using it on your own data

Write a mapping for your extract outside the repository (for example in a
gitignored `private/` folder), validate it, and run. **Never commit real data**
— see [docs/CONTRIBUTING.md](docs/CONTRIBUTING.md).

## Project layout

```
workbench/   engine: cli, mapping, sources, loader, integrity, runner, materiality, workpaper, runlog, pipeline,
             review + review_app (optional review screen)
packs/       test packs (folder = meta.yaml + test.sql)
mappings/    commented example mappings
sample_data/ synthetic data + planted issues
tools/       synthetic data generator
tests/       unit and acceptance tests
docs/        design, plan, mapping and pack guides
```
